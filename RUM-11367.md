[C++] Implement RUM sessions

Design the C and C++ APIs used to "create a session and manage its lifecycle," implement those APIs, and implement the internal state required by the RUM feature to track sessions and generate session-scoped events.

D.o.D.

- Both C and C++ APIs have functions for starting and stopping session scope
- In the RUM feature implementation, we update our internal state in response to these API calls, such that we could populate any RUM event with session-related properties, once such events are implemented
- Example programs create a RUM session, but do not need to send events (until RUM-11368is done)

## Questions

1. **Session Lifecycle**: Should sessions start automatically on first view/action (per design docs) or require explicit start calls? The DoD mentions "starting session scope" which suggests explicit APIs, but the design docs favor automatic startup.

2. **Session Sampling**: Should sampling be determined at session start or at RUM feature initialization? How should sampled-out sessions behave (null UUID vs normal UUID with dropped events)?

3. **Session Timeout**: Should we implement automatic session timeout in this work item, or defer that complexity? If implemented, should it run on a background timer or check on each API call?

4. **Session Storage**: What session properties need to be tracked internally? Session ID, start time, last activity, sampling status, view count, etc.?

5. **Thread Safety**: Sessions will be accessed from multiple threads (main thread for API calls, background for timeout). What synchronization strategy should we use?

6. **Session Events**: Should session start/end events be generated in this work item, even though views aren't implemented yet?

### Step 11: Implement Session Event Generation
**Internal event structure (JSON):**
```json
{
  "type": "session",
  "event": "start" | "end", 
  "session_id": "uuid-string",
  "timestamp": milliseconds_since_epoch,
  "application_id": "app-id",
  "duration": milliseconds (for end events)
}
```

- Generate session start events on session creation
- Generate session end events on manual stop or timeout  
- Store events in feature's storage queue (but won't be uploaded until proper report generation)
